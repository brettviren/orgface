#+title: Embeddings in the store
#+filetags: :concept:developer:search:
#+summary: How vectors are kept per model identity, and kept out of the write path.
#+audience: developer
#+status: current
#+updated: 2026-08-23
#+source: src/org_store/embed.py
#+source: src/org_store/backends/sqlite.py

A vector stands for a node's meaning, and is what
[[file:semantic-search.org][semantic search]] compares. Each model identity has a vector space: a row in
=vector_spaces= giving its width, and a =sqlite-vec= virtual table named
=vec_space_<id>= holding its vectors. The =embeddings= table records, per
node and space, a hash of the text that was embedded and the row id of the
vector.

A space's table cannot be created with the rest of the schema: its width
is the model's dimension count, not known until that model is first used.

* Not a derived table

Everything else the store derives — tags, links, full text — is recomputed
on every write. Embeddings are not, because they are not free: they cost a
call to a model that may not even be running. A write that depended on one
would fail for a reason having nothing to do with storing a document.

So embedding is asked for, by =org store embed=, and the store keeps enough
bookkeeping to make that cheap.

* Incremental by text hash

A node whose text has not changed since it was embedded is left alone. Most
of a document is unchanged on most writes, so this is the difference
between an edit costing one call and costing hundreds.

Vectors for nodes that no longer exist are dropped in the same pass, from
every space, so the index does not accumulate orphans. That is judged
against the whole store, so embedding some documents leaves the rest alone.

* One space per model identity

Vectors from two models do not live in the same space, and comparing them
would silently return nonsense. So each identity gets its own space, and
embedding or searching with one never touches another's. A store shared
between machines can therefore hold vectors from each machine's model at
once, and several services naming one model differently share a space by
sharing an identity.

A space keeps the width it was made with; a model claiming an identity
with another width is refused rather than mixed in.

Which service to use is the service layer's choice, not the backend's:
=OrgStore= holds the configured embedders in order and passes the chosen
one to =embed= and =semantic_search=.

* Stores from before vector spaces

Their =embeddings= table tagged each vector with a model name, in one
=vec_nodes= table. Opening one drops both, keeping every document;
=org store embed= makes the vectors again.

* Filtering after the search

Nearest-neighbour search knows nothing about tags, properties or document
ids, so it is asked for more rows than the query wants and the qualifiers
are applied afterwards. That is why =top_k= is a request rather than a
promise when qualifiers are in play.
