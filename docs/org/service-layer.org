=OrgStore= wraps one [[file:backend-protocol.org][backend]] and offers CRUDS over it. It is the only
layer that knows what an operation *means*: which refs a document ends up
with, what has to be re-derived after a write, and what a caller may
address.

Anything a second adapter would otherwise have to reimplement belongs here.
That is why the views it returns — =DocumentSummary=, =NodeSummary= — are
already-computed facts rather than models an adapter would have to walk.

* Create settles the id first

Refs are a function of the document id, so the id has to be known *before*
refs can be assigned. The backend is therefore asked to allocate an id, the
document gets its refs, and then it is written — once. Folding the two
together would store the document twice and leave it briefly persisted
under refs nobody can address.

* Read reassigns refs too

Refs are recomputed on read rather than trusted from the backend. They are
a pure function of the id and each node's structural path, so recomputing
is cheap and always right — and it is the only thing that makes the
[[file:backend-orgfs.org][org file store]] addressable at all, since org text has nowhere to keep a
ref. A backend that persists them is caching what this would have worked
out anyway.

* Node operations live here, not in backends

Addressing a node means walking the canonical tree, and *writing* one means
reassigning the refs of everything after it. A backend offering
=update_node= would either duplicate that walk or write a node and leave
the document's refs stale. Both are expressed once here, over
=read_document= and =replace_document=.

* Capabilities are asked for, not assumed

Search, reindex and embed are not on the backend protocol. The service asks
whether the active backend can do them and, when it cannot, says so — an
empty result would read as "no matches" when it means "never looked".

* Choosing an embedding service

=OrgStore= is given the configured embedders, in order. =embed= uses the
first that answers, of the requested identity when there is one; a
semantic =search= also passes over any whose identity has no vectors in
the backend. The backend is handed the chosen embedder and never chooses
one itself, so the policy is the same for every adapter.
