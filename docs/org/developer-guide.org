For someone changing org-cli-helper. The same pages as the
[[file:user-guide.org][user guide]] and several more, ordered for a reader who needs to know why
the code is shaped as it is before touching it.

* Before the first change

#+begin_src sh
uv sync                              # every extra, so the whole suite runs
uv run pytest -m "not emacs"         # fast pass
uv run python -m org_store.schema    # regenerate the committed schema
#+end_src

Read [[file:layering.org][The layering rule]] first. It is the constraint most likely to be
broken by a plausible-looking change, and the one that everything else
depends on.

* Where a change goes

- A new command :: a module under =commands/=, registered in =cli.py=,
  calling into a data module. See [[file:layering.org][The layering rule]].
- A new setting :: one entry in =SETTINGS=. See [[file:configuration.org][Configuration]].
- A new backend :: one entry in the backend table plus the module. See
  [[file:backend-protocol.org][The backend protocol]].
- A new indexed fact :: the extraction rules, then =org store reindex=. No
  migration. See [[file:derived-index.org][The derived index]].
- A new node type :: a model class, a template, and a line in the walker's
  dispatch table. See [[file:canonical-document.org][The canonical document]].
- A new operation for agents :: a route in the HTTP API; the MCP tool
  follows. See [[file:http-api.org][The HTTP API]].

* And the documentation

Code and documentation are meant to move together. Each page names the
files it describes, so a change to a file says which pages to revisit;
[[file:documentation-wiki.org][This documentation wiki]] explains the convention and the checks that enforce
it.
