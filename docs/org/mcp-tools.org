Nothing in the MCP module describes a tool. The tools come from the
[[file:http-api.org][HTTP API]]'s OpenAPI document, so each one's name, arguments and result are
the operation's own. There is no second description to keep in step with
the first, and adding a route adds a tool.

That is the whole reason the FastAPI layer is real rather than a schema
exercise. The MCP server calls it *in process*, over an ASGI transport,
with no socket and no port.

* What the server tells an agent

Instructions travel with the server, because the things an agent gets wrong
here are not guessable from a tool signature:

- A document is addressed by its id, which =list_documents= reports.
- Each node has a [[file:node-refs.org][ref]], which =search= returns and =read_node= takes.
- Refs name *positions*: an insert or a delete changes the refs of
  everything after it, so re-read a document before reusing an old ref.
- The identifier that survives editing is org's own =ID= property.
- [[file:command-search.org][Search]] matches words literally, so punctuation and maths need no
  escaping; =semantic= matches by meaning and only finds what is embedded.
  Both =search= and =embed= take an optional =identity= naming the model
  whose vectors to use; without one, the first configured service that
  answers is used.

* Naming

Tool names are the operation ids, so the HTTP operation and the tool are
unmistakably the same thing. =org mcp --list-tools= prints them with the
first line of each description.
