=-s/--semantic= matches on meaning rather than on words.

#+begin_src sh
org store embed              # build the vectors; only changed text is sent
org store embed -i nomic     # ... with a service of that model identity
org store embed status       # vectors per identity, and which services answer
org search -s "physics equations"
org search -s -i nomic "physics equations"
#+end_src

Word search finds nothing for "physics equations" in a note that says
=\begin{equation} \nabla \cdot \mathbf{E} = ...=. Semantic search finds it.

The same =-t=, =-T=, =-p= and =-d= qualifiers apply. =--scope= does not: a
vector is of the whole node, not of its heading or its body.

Each hit is led by its cosine similarity to the query: 1 for the same
meaning, near 0 for unrelated. What counts as a good match varies by
model, so compare scores within one search rather than across models.

* Embedding is a separate step, on purpose

It costs a call to a model that may not be running, and storing a document
should not fail for that reason. So =org store embed= is asked for, and it
is incremental: a node whose text has not changed is not sent again.

* Several services, several models

Configuration may name any number of embedding services, as repeated
=[[embed]]= tables, in the order to try them (see [[file:configuration.org][Configuration]]). Each has
a =url=, the =model= name that service uses, and an =identity= saying which
model it really is, defaulting to =model=.

Vectors are kept per identity. Services name the same model differently —
one serves =nomic-embed-text=, a local =llama-server=
=nomic-embed-text-v1.5= — and nothing they report identifies the weights
behind a name, so the configuration says which names are one model: give
them the same =identity= and the vectors either makes serve both.
Different identities keep separate vectors side by side, so a store shared
between machines can hold what each embedded with its own model.

- =org store embed= :: uses the first service that answers, among those of
  =-i/--identity= when given. Answering means a one-word embedding came
  back from that model with the configured width.
- =org search -s= :: the same, but skips any service whose identity has no
  vectors in the store: an empty index would answer, uselessly.
- =org store embed status= :: the vectors each identity has, then every
  configured service with its identity, url, model and whether it answers.

Texts are sent =batch= to a request, =parallel= requests at a time, and
both are lowered with a warning when a service turns out not to manage
them (see [[file:configuration.org][Configuration]]). More in parallel mostly helps a remote service,
where each request spends much of its time on the network, or a
=llama-server= started with =--parallel=.

Be careful an identity is true. Two different models under one identity
mix two vector spaces and search quietly returns nonsense. A model whose
width differs from the vectors already under its identity is refused.

* Questions and passages are embedded differently

nomic-embed-text is trained asymmetrically: a passage is prefixed
=search_document:= and a question =search_query:=, and embedding both the
same way measurably worsens retrieval. That is a difference in the
interface — two methods on the embedder — rather than a flag somebody can
forget.

* What it needs

The default expects [[https://github.com/ggml-org/llama.cpp][llama.cpp]]'s =llama-server= on =127.0.0.1:8080=
serving nomic-embed-text, and the =semantic= extra for the vector index:

#+begin_src sh
llama-server -m ~/models/nomic-embed-text-v1.5.Q8_0.gguf --embeddings
uv sync --extra semantic
#+end_src
