The backend protocol

reference developer store

A backend knows how to keep documents somewhere and nothing else. The protocol is small on purpose.

allocate_id(path_hint)
choose the id a document would get, without storing it.
create_document(doc, path_hint)
store a new document, return its id.
The rest of CRUD
=read_document(doc_id)=, =replace_document(doc_id, doc)=, =delete_document(doc_id)=, =list_documents()=.
content_hash(doc_id)
the digest sync compares.

allocate_id is separate from create_document because refs are a function of the document id, so the service must know the id before it can assign refs and write once. A path_hint is a request, not an instruction: a backend may use it as the id, as a filename, or ignore it.

What is not in it

Search
not every backend can answer a text or vector query at all. In the contract, every backend would have to reimplement or fake it.
Node reads and writes
addressing a node is a walk of the canonical tree, and writing one means reassigning refs — a rule the service owns.
Validation
a backend is handed documents that are already valid.

Errors are typed

DocumentNotFound, NodeNotFound, DocumentExists and InvalidDocument all derive from StoreError. Every adapter already handles StoreError, and none of them should have to import pydantic to report a bad document — so a validation failure is re-raised as one of these at the service boundary.

Registering one

Backends are entries in a table: name, how to open it, which configuration setting locates it, its default location under the state directory, whether it needs an Emacs, and a summary. Adding a backend is that entry plus the module.
