Architecture

concept developer

The store half is ports and adapters. One canonical model at the centre, several kinds of storage below it, several front ends above it, and exactly one layer that knows what an operation means. 

        CLI          HTTP API         MCP tools        <- adapters
          \             |               /
           \            |              /
            +---- service layer (CRUDS) ----+          <- the only decisions
                        |
       +----------------+----------------+
    sqlite           org files        via Emacs        <- backends
       +----------------+----------------+
                        |
              canonical document model                 <- one shape

The rule

The service layer is the only thing that knows CRUDS semantics. Adapters are thin and call it. Backends are the only things that know about sqlite, org-parser, Jinja2 or Emacs. Sync talks to stores exclusively through the service layer, never by reaching into one backend's internals to shortcut into another's.

State that rule and most design questions answer themselves: where does validation go (service), where does "what is a tag" go (the extraction rules, beside the model), where does "which backend is active" go (configuration, resolved once).

Two packages

org_store
the library — model, backends, service, search, sync, renderer, HTTP and MCP. It never imports org_cli_helper.
org_cli_helper
the CLI. Argument parsing, presentation, Emacs daemon management, configuration, and the capture commands.

The dependency runs one way, which is what lets the store be used without the CLI — and what forces the Emacs backend to declare a port for the Emacs it needs rather than importing one.

Where the capture half sits

It is older and simpler: commands over data modules, with emacs.py as the one channel to Emacs. It shares configuration, the XDG conventions and the ui module with the store half, and nothing else.
