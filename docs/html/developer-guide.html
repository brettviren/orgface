Developer guide

guide developer

For someone changing orgface. The same pages as the user guide and several more, ordered for a reader who needs to know why the code is shaped as it is before touching it.

Before the first change

uv sync                              # every extra, so the whole suite runs
uv run pytest -m "not emacs"         # fast pass
uv run python -m org_store.schema    # regenerate the committed schema

Read The layering rule first. It is the constraint most likely to be broken by a plausible-looking change, and the one that everything else depends on.

Where a change goes

A new command
a module under commands/, registered in cli.py, calling into a data module. See The layering rule.
A new setting
one entry in SETTINGS. See Configuration.
A new backend
one entry in the backend table plus the module. See The backend protocol.
A new indexed fact
the extraction rules, then org store reindex. No migration. See The derived index.
A new node type
a model class, a template, and a line in the walker's dispatch table. See The canonical document.
A new operation for agents
a route in the HTTP API; the MCP tool follows. See The HTTP API.

And the documentation

Code and documentation are meant to move together. Each page names the files it describes, so a change to a file says which pages to revisit; This documentation wiki explains the convention and the checks that enforce it.
