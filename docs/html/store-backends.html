Store backends

concept user developer store

Three, chosen with store.backend. All answer the same commands.

sqlite
the default. One database, with the derived indexes that make search possible. Nothing but this tool reads it.
orgfs
ordinary org files in a directory. Nothing to import, no search index, and Emacs and git are first-class writers.
emacs
the same files, read through your running Emacs. Slower, needs ox-json, and is the only reader that is definitionally right.

Which one is active is a configuration question, not a command line one, so it is resolved once and every command sees the result. Each backend declares which setting locates it — sqlite wants store.database, the file backends want store.directory — so the code that opens one does not have to know that.

What a backend is, and is not

A backend knows how to keep documents somewhere, and nothing else. It does not validate, does not decide what a ref means, and does not search. That belongs to the service layer above it. See The backend protocol for the whole contract.

Adding one

An entry in the backend table: a name, how to open it, which configuration setting locates it, where it lives when configuration is silent, whether it needs an Emacs, and a one-line summary. Adding a backend is that entry plus the module — not an edit to the code that opens one, and not a change to any adapter.

Moving between them

Content is not trapped in whichever you chose. org store sync copies in either direction, and it can tell what has actually changed because a content hash means the same thing in all three.
